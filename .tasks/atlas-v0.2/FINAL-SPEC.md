# Atlas v0.2 Final Implementation Spec

- **Status:** implementation candidate
- **Date:** 2026-07-15
- **Target branch:** `codex/aakb-atlas-v0.2` (forked from `v0.2-ui`)
- **Primary visual source:** `src/app/mockup/`
- **Release emphasis:** real API, Atlas Image pipeline, Bunny storage, OpenAI generation/transcription, device authentication, and CLI/agent access

## 1. Source-of-truth order

Use this order when implementation details conflict:

1. This specification owns data, API, storage, security, and release boundaries.
2. The 16 screens in `src/app/mockup/` own the intended visual hierarchy, copy, controls, user-visible states, and navigation shape.
3. Existing routes and components under `src/app/files/` and `src/features/` provide reusable conventions but may be changed to match the mockup.
4. Earlier questionnaire decisions remain valid unless the newer mockup clearly supersedes them. The four-step new-file wizard is one deliberate supersession of the earlier minimal form.

The mockup route is a design artifact. Production screens must use persisted data and real actions rather than importing `mock-data.ts`.

## 2. Release objective

Atlas v0.2 must let one renovation company approve a device, unlock Atlas with a per-device PIN, create and manage renovation files, capture or upload job photos, annotate those photos, select a source image and curated references, give text or voice direction, generate one renovation concept through OpenAI, store every original and generated image in Bunny, revisit generation history and lineage, and expose the permitted file/reference operations to local AI agents through an Atlas CLI backed by an authenticated HTTP API.

## 3. Platform and responsive boundary

### Required

- Desktop browsers.
- iPad in landscape orientation, including touch targets and camera/file-picker behavior.
- Layouts from 1024 CSS pixels upward must be first-class and must not require horizontal page scrolling.
- The desktop two-column direction/reference workspace may stack at narrower iPad widths if both surfaces remain easy to reach.

### Best effort only

- Phone and portrait layouts should remain usable for authentication, capture, and basic navigation.
- The existing portrait/mobile mockup is a graceful fallback, not a pixel-parity release requirement.
- Do not spend release time reproducing every desktop detail on a phone.

### Navigation shell invariant

The existing production navigation shell is part of Atlas's identity and is not a redesign target.

- Keep the production `AtlasTopbar` structure, breadcrumb behavior, actions, spacing, and visual treatment. New screens must compose inside it rather than introduce a replacement header.
- Reuse the production bottom-navigation pattern wherever a screen has sibling file sections, wizard progression, pipeline stages, or paired primary/secondary actions.
- Preserve the established full-width sticky bottom bar, shared frame alignment, safe-area padding, and large touch targets.
- The mockup's `MockTopbar` and `MockBottomNav` are visual copies of the production components. Implementation must extend/reuse `AtlasTopbar`, `FileBottomNav`, and a shared production bottom-action primitive instead of shipping parallel mock navigation components.
- Milestone reviews must explicitly compare the production top and bottom navigation before and after the change. Navigation chrome changes are a failure unless required for a new breadcrumb label or new bottom-bar action.

## 4. Product model

- One **File** represents one renovation opportunity at one property.
- A file may contain multiple rooms or renovation areas.
- **File Images** are job-specific site photos and generated concepts embedded in File Details.
- The **Reference Catalog** is company-wide, curated generation input and is separate from File Images.
- A generation always has one explicit source image. There is no persistent file-level “active photo.”
- A completed generated image may become the next source via **Continue editing**.
- One concept is generated by default per run.
- Every completed output is saved immediately and retained in chronological history.

## 5. Canonical user flows

### 5.1 Sign in with Clerk

Clerk replaced device enrollment and the PIN in v0.6.0 (VAR-27). Device, PIN and session-cookie text elsewhere in this spec is historical.

1. Atlas uses the existing Clerk Development instance of the AAKB Atlas application. Google is the only sign-in method.
2. A signed-out visitor to any page is sent to `/sign-in`, which shows Clerk's `<SignIn />` with "Continue with Google". `/login` redirects there.
3. After Google sign-in, Atlas reads the user's primary email from Clerk. Access needs that email to be verified and listed in `ATLAS_ALLOWED_EMAILS`, a comma-separated list compared without regard to case.
4. A signed-in account that is not on the list sees `/not-authorised`, which names the account and offers sign out. API routes answer it with 403 `not_authorised`.
5. A signed-out API request gets 401.
6. **Sign out** ends the Clerk session and returns to `/sign-in`. Clerk owns session lifetime; Atlas keeps no session table or cookie of its own.
7. `requireAuth()` (pages and server actions) and `getAuthenticatedSession()` (API routes) in `src/services/auth/session.ts` make every access decision. `src/proxy.ts` runs `clerkMiddleware()` so those guards can read the session; it does not decide access itself.
8. Local development only: with `ATLAS_DEV_AUTH_BYPASS=1` and `NODE_ENV` other than `production`, both guards return a fixed `dev@local` session, Clerk is skipped entirely and no keys are needed.

The CLI and admin API keep their own `ATLAS_CLI_ADMIN_TOKEN` bearer token and do not use Clerk.

### 5.2 Create a file

The new-file form is a four-step wizard:

1. **Basics:** file name and project type.
2. **Scope:** job type, budget range, and lead source.
3. **Pipeline:** relationship status (Prospect, New lead, Qualified lead, Client, Bounced, Archived) and workflow stage (New file, Site Visit, Design Concept, Proposal, Accepted, Archived). A new file defaults to New lead and New file.
4. **Contact:** contact name, email, phone, and note.

Required fields are file name, project type, and contact name. All current detailed fields remain available; the wizard changes presentation, not the underlying file record.

The final step offers:

- **Create only, without a photo** -> save and open File Details.
- **Create & take first photo** -> save and open the capture flow for that file.

### 5.3 Capture, upload, and annotate a site photo

1. Open capture from the new-file completion action, File Images, or Atlas Image source selection.
2. On supported devices, use the camera with upload/file-picker fallback.
3. Review one photo before saving.
4. Optionally assign camera position, room/area, and label.
5. Save the local record and upload the bytes through Atlas to Bunny.
6. Show an honest uploading/failed/ready state. A failed upload remains retryable and must not appear fully saved.

Bulk rapid capture is not required in v0.2. The expected loop is capture -> review -> save -> capture next.

### 5.4 File Images

File Images remain embedded inside File Details as a dedicated internal view/tab. They provide:

- capture and upload actions;
- search by label and tag;
- filters for all, site photos, and generated images;
- room filters, including **No room**;
- visible room, camera-position, type, and origin metadata;
- image detail/metadata editing;
- **Use in Atlas Image** for valid source assets;
- useful empty and no-results states.

### 5.5 Atlas Image

Atlas Image is a staged pipeline:

1. **History:** chronological generations for the file; start a new generation, open a result, retry a retryable run, or inspect a blocked reason.
2. **Source:** choose exactly one source using Take Photo, Use Library, or Upload. File Images and previous generated outputs are valid library sources.
3. **Direction & references:** an append-only user direction log on the left and categorized reference selection on the right. Several references may be pinned across categories. Voice recording returns an editable transcript to the composer and never auto-adds or auto-generates.
4. **Generate & result:** request one concept, show generating progress, save a successful output immediately, and distinguish retryable provider failures from policy-blocked requests.
5. **Continue editing:** make the completed output the new source, preserve lineage, and continue in the same image thread.
6. **Generation detail:** show before/after first; reveal direction, references, lineage, provider/system metadata, source-photo link, regenerate, and continue-editing actions.

The direction area is not an assistant conversation. Atlas must not call a text LLM to acknowledge, summarize, or reply with messages such as “Got it” or “I'll keep the window.” The user edits the current composer draft, then adds it as the next immutable direction entry. Corrections are additional entries. When **Generate concept** is clicked, Atlas snapshots the ordered direction entries plus the currently pinned references and sends that complete bundle to the image-generation job.

References are optional but recommended. The selected source and references remain visible while direction entries are composed.

### 5.6 Reference Catalog

- The UI is browse/search/filter only.
- The first seeded taxonomy is bathroom-oriented but extensible: Vanities, Baths, Sinks, Toilets, Showers, Racks, Tapware, Materials, Flooring, Lighting, Mirrors, and Benchtops.
- Categories are data, not a hard-coded union, so agents can add more later.
- Reference uploads and category creation occur through the CLI/API, not through a web admin screen in this release.

## 7. Image metadata contract

### Shared fields

- `id`
- `fileId`
- `kind`: `site_visit | ai_generated`
- `origin`: `camera | upload | generated`
- `label`
- `room`: nullable string
- `tags`: ordered string array
- `storageKey`
- `cdnUrl` or a deterministically derived URL
- `mimeType`, `byteSize`, `width`, `height`
- `uploadStatus`: `pending | ready | failed`
- `createdAt`, `updatedAt`

### Camera-position field

Store this as `cameraPositionClock`, not a generic `direction`, because it describes where the camera stood relative to the door.

Allowed values are nullable and limited to:

| Value | Meaning |
|---|---|
| `12` | At the door |
| `2` | Front-right corner |
| `3` | Right of the door |
| `4` | Back-right corner |
| `6` | Opposite the door / back wall |
| `8` | Back-left corner |
| `9` | Left of the door |
| `10` | Front-left corner |

The door is always the 12 o'clock anchor. The field is optional during capture and editable later. Tapping the selected value again clears it. The current mockup phrase “Facing the door” for `6` should be treated as copy ambiguity; the stored semantic is camera position, not facing direction.

Generated assets inherit the source room when available, but do not receive a camera-position value. Their source/parent relationships remain visible through generation lineage.

## 8. Persistence model

The current schema is insufficient. Add or evolve the following persisted concepts.

### Existing tables to extend

- `files`: retain the complete wizard fields.
- `primary_contacts`: retain one primary contact per file for v0.2.
- `file_notes`: retain appendable file notes.
- `file_assets`: add the image fields in section 7 and an optional `generationId`.
- `pipeline_runs`: either evolve into generation runs or keep as the high-level pipeline record linked to a generation.

### New tables

- `device_enrollments`: code, device name, normalized public key, server-computed fingerprint, proof state, approval state, expiry, timestamps.
- `devices`: approved public key/fingerprint, status, PIN hash/salt, PIN-reset flag, failed-attempt counters/lock time, timestamps.
- `auth_challenges`: device, purpose, canonical payload, expiry, consumed time.
- `device_sessions`: opaque hashed session token, device, last activity, expiry/revocation.
- `reference_categories`: slug, label, sort order, timestamps.
- `reference_images`: category, label, tags, Bunny storage facts, creator/audit fields, timestamps.
- `atlas_image_threads`: file, root source asset, timestamps.
- `atlas_image_direction_entries`: thread, ordered sequence, text, source (`typed | transcription`), timestamps. Entries are user-authored and immutable after being added.
- `atlas_image_generations`: thread, parent generation, source asset, output asset, status, compiled prompt, provider request identifier, model, quality, error class/message, timestamps.
- `generation_references`: generation/reference join table preserving selection order.

Foreign keys and unique constraints must prevent cross-file lineage and duplicate active device fingerprints.

### Database ownership

The current `sql.js` database is owned by the Atlas process and persisted as a whole file. The CLI must never mutate that file directly. All CLI reads and writes go through the authenticated Atlas HTTP API so there is one database owner/writer.

## 9. HTTP API contract

Exact internal filenames may vary, but the behavior below is required. All mutations validate input with shared schemas and return structured JSON errors.

### Sign-in

- Sign-in, sign-out and session handling are Clerk's (see 5.1). Atlas exposes no auth endpoints of its own.
- Every browser-facing API route answers 401 when signed out and 403 `not_authorised` for an account off the allowlist.

### Files and assets

- list/get/create/update files;
- list assets with kind, room, tag, and search filters;
- upload one site/reference image through Atlas;
- get asset metadata and retrievable content/URL;
- patch only label, room, tags, and nullable camera position for ordinary image metadata editing.

### References

- list/search categories and reference images for authenticated UI/device clients;
- CLI-admin create category;
- CLI-admin upload reference image with category, label, and tags;
- no reference delete command in v0.2.

### Atlas Image

- list file generation history;
- get generation detail and lineage;
- create a generation from one source asset, ordered reference IDs, and direction text;
- append user direction entries to a thread; there is no assistant-message endpoint;
- retry eligible failed generations without overwriting the original record;
- continue editing from a completed output by creating a child generation/thread step;
- transcribe a bounded voice clip and return text for editing.

Generation creation must be idempotent per client request ID so an iPad retry cannot create duplicate billed runs.

## 10. Bunny integration

- Bunny is canonical production storage for original photos, uploads, reference images, and generated outputs.
- The browser uploads to Atlas. Atlas validates type/size and then uploads to Bunny; Bunny credentials never reach the browser.
- Suggested keys:
  - `files/<fileId>/site/<assetId>.<ext>`
  - `files/<fileId>/generated/<assetId>.<ext>`
  - `references/<categoryId>/<referenceId>.<ext>`
- Persist the storage key only after Bunny accepts the bytes. Derive or persist the CDN URL consistently.
- Local filesystem storage is a development fallback only and must be explicit in configuration.
- If database persistence fails after a Bunny upload, record/emit enough information to reconcile the orphaned object.

## 11. OpenAI integration

### Image generation

Use the Image API edits endpoint with `model: "gpt-image-2"`. Atlas performs one direct image job when the user clicks **Generate concept**; it does not run a separate conversational model. The Image API accepts one or more reference images, so the ordered input array is:

1. the structural source/before image;
2. every pinned catalog reference in selection order.

The compiled prompt must label those roles explicitly, preserve the room geometry and requested invariants, and append every user direction entry in chronological order. Continue editing is another direct edit job whose first input is the chosen prior output; it does not depend on provider conversation state.

`gpt-image-2` supports `medium` and `high` output quality and processes image inputs at high fidelity automatically. Configure quality through `ATLAS_IMAGE_QUALITY=medium|high`. Use `medium` during initial integration, then perform a controlled medium-versus-high comparison at the Milestone 3 human gate using the same source, references, and direction. The user chooses the production default after reviewing fidelity and latency. Persist the actual model and quality on every generation.

For each run:

1. Load the source and selected reference image bytes/URLs from Bunny through the server.
2. Compile a provider prompt that clearly distinguishes the structural source photo, ordered user direction entries, and optional style/product references.
3. Create a pending generation record before the provider call.
4. Call `images.edit` with GPT Image 2, one output, and the configured medium/high quality.
5. Store the provider request ID, model, and quality for audit.
6. Decode the returned image, upload it to Bunny, create the output asset, and atomically mark the generation complete.
7. Classify timeouts/transient provider errors as retryable and policy/content refusals as blocked.

Official implementation references: <https://developers.openai.com/api/docs/guides/image-generation#edit-images> and <https://developers.openai.com/api/docs/guides/image-generation#customize-image-output>.

### Voice transcription

Use the request-based Audio Transcriptions API for short, bounded recordings. `gpt-4o-transcribe` is the quality default; make the model configurable. The server accepts the recorded `webm`, `m4a`, `mp4`, `mp3`, or `wav` clip, sends it to OpenAI, returns transcript text, and discards the temporary audio unless a later product decision explicitly retains it.

The transcript lands in the composer and remains editable. The user must explicitly add it to the direction log. It must not auto-add, auto-submit, or automatically start generation.

Official implementation reference: <https://developers.openai.com/api/docs/guides/speech-to-text>.

## 12. CLI and AI-agent contract

Provide an `atlas` CLI that talks to the running Atlas HTTP API using an admin bearer token stored outside the repo. Output is clean on stdout and diagnostics go to stderr.

### Required commands

- `atlas files list|search|get`
- `atlas assets list|search|get|content`
- `atlas assets edit <id> --label ... --room ... --tags ... --clock ...`
- `atlas references categories list|create`
- `atlas references list|search|get|upload`

### Output modes

- compact human/agent view by default;
- `--json` for stable machine-readable output;
- binary asset content writes only to an explicit output path or stdout when explicitly requested;
- stable nonzero exit codes and structured errors.

### Authority limits

- No direct database access.
- No file deletion, asset deletion, generation invocation, or broad file edits in v0.2.
- Image metadata edits are limited to label, room/category where applicable, tags, and nullable clock position.
- Reference category creation and global reference upload are intentionally permitted.

## 13. Security requirements

- Public deployment is allowed only over HTTPS.
- Browser access requires a Clerk session whose verified primary email is in `ATLAS_ALLOWED_EMAILS`. Clerk keys live only in `.env`.
- Rate-limit CLI-admin auth.
- Apply a restrictive CSP that allows only the Clerk hosts sign-in needs, and do not run analytics/session replay on the sign-in page.

This is a deliberately smaller product slice than the full PGPAuth design. WebAuthn PRF protectors, recovery credentials, multiple subjects, and multi-tenant identity are deferred.

## 14. Status and error semantics

### Uploads

- `pending`, `ready`, `failed`

### Generation

- `generating`: provider/storage work is active.
- `complete`: output exists in Bunny and File Images.
- `retryable`: transient provider/network/storage failure; original run remains in history.
- `blocked`: provider policy/content refusal; prompt must be revised.
- `failed`: non-retryable internal consistency failure; visible in diagnostics/history even if the primary UI collapses it into an error state.

Cancel is best-effort. If the provider cannot be cancelled and later returns an image, Atlas must not silently attach it as a successful user-visible result after the run was marked cancelled.

## 15. Three implementation milestones and human gates

This release must be implemented as three separately dispatched packets. The implementation agent stops after each milestone, writes its evidence report, and waits for explicit user approval. It must not begin the next milestone because the previous code compiles.

### Milestone 1 — foundation, authentication, new file, and Reference Catalog

Implement the schema/API foundation needed by this slice, device enrollment/unlock/reset/revoke, the four-step new-file wizard, the real browse-only Reference Catalog, and CLI device/reference commands. Connect Bunny for real reference-image upload and retrieval. Preserve the production top navigation and use the production bottom-bar pattern for wizard progression.

**Human gate:** the user supplies local secrets without committing them, approves a real device through the CLI, tests PIN behavior and the new-file wizard, uploads/browses a real Bunny reference, and confirms the production navigation remains unchanged. Stop here until approved.

### Milestone 2 — File Details and Site Images

Implement the File Details/Images sibling views, production bottom navigation, camera/file-picker capture, Atlas-mediated Bunny uploads, gallery/search/filters, metadata editor, optional eight-position camera location, room/tags/labels, and real upload failure/retry states.

**Human gate:** the user tests from an iPad in landscape, captures and uploads real images, confirms Bunny persistence and metadata round trips, and approves the Details/Images bottom-navigation behavior. Stop here until approved.

### Milestone 3 — Atlas Image pipeline

Implement generation history, source selection, append-only direction entries, voice transcription into an editable draft, multi-reference selection, GPT Image 2 jobs, Bunny output persistence, complete/retryable/blocked states, generation detail, and continue-editing lineage.

**Human gate:** the user supplies the OpenAI key, verifies account access to GPT Image 2, runs the same representative job at medium and high quality, chooses the production default, and tests generation/history/continue-editing end to end. Stop after the report; no release commit or push without separate approval.

## 16. Binding release acceptance

1. All 16 mockup screen contracts have a production route/state or an explicitly documented fallback.
2. No production screen imports mock data.
3. A new device can enroll, be CLI-approved, set a PIN, unlock by key proof plus PIN, lock after inactivity, reset PIN, and be revoked.
4. The old shared-password login is removed from the production path once device auth is active.
5. The four-step file wizard persists the complete existing file/contact/note fields and supports both completion actions.
6. iPad landscape can capture or upload a photo, review it, save optional metadata, and find it in File Images.
7. Camera position accepts only nullable `12|2|3|4|6|8|9|10` and is editable later.
8. Original, uploaded, reference, and generated image bytes are canonical in Bunny in production.
9. File Images support the mockup's search, kind filters, room filters, metadata detail, and Atlas Image action.
10. The web Reference Catalog is browse-only; the CLI can create categories and upload references.
11. An authenticated user can select one source, select several references, append user-only direction entries, transcribe voice into an editable draft, explicitly add that draft, and request one GPT Image 2 concept with no assistant text replies.
12. Every completed output is immediately stored, appears in File Images/history, and retains source, compiled direction, references, provider request ID, model, quality, and lineage.
13. Continue editing uses the chosen output as the next source without destroying the prior generation.
14. Generating, complete, retryable, and blocked UI states are driven by persisted server state.
15. CLI list/search/get/content and narrow metadata/reference/device commands use the authenticated HTTP API and never touch SQLite directly.
16. Desktop and iPad-landscape flows have no horizontal page overflow and retain usable sticky actions/touch targets.
17. `bun run lint` and `bun run build` pass.
18. Automated tests cover auth challenge replay, PIN rate limiting, metadata validation, generation idempotency, and continue-editing lineage.
19. The production `AtlasTopbar` structure and visual treatment remain unchanged, and shared production bottom navigation is used for file sections, wizard stages, and pipeline actions wherever represented in the mockup.
20. Milestone 1, 2, and 3 each have a separate ACHIEVED report and explicit human approval before the next packet begins.

## 17. Non-goals

- Phone-first or portrait pixel parity.
- Multi-company tenancy or named staff accounts.
- A web admin UI for reference uploads, category creation, or device approval.
- Direct browser uploads to Bunny.
- Direct CLI access to the `sql.js` file.
- Multiple generated concepts by default or automatic fusion of several source photos.
- Image/record deletion workflows.
- Full PGPAuth library extraction, WebAuthn integration, recovery codes, or hardware-backed assurance.
- Kitchen/laundry-specific reference taxonomies beyond the extensible category model.
- Storing voice recordings as file notes.
- Text-LLM acknowledgements, assistant chat replies, or an LLM-generated intermediate brief before image generation.
- Redesigning or replacing the production top navigation shell.

## 18. Implementation assumptions to preserve

- The mockup's newer four-step wizard intentionally supersedes the earlier two-field-first form decision.
- iPad landscape and desktop are the release-quality targets; phone UI remains graceful only.
- `cameraPositionClock` records camera location, not lens heading.
- Generated images inherit room metadata from their source when present but carry lineage instead of a camera position.
- PIN reset preserves the approved device key but revokes sessions and requires fresh key proof before setting a new PIN.
- The API and model strings are configurable through environment variables; domain records retain the actual provider/model used for each generation.
- The production top navigation is preserved. New work extends the shared production bottom-navigation pattern.
- Direction is a user-only append log. Generate Concept sends the source, pinned references, and ordered entries directly to GPT Image 2.
- GPT Image 2 quality remains configurable until the Milestone 3 medium/high human comparison selects the production default.
